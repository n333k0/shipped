# Technical standards

Sources: `pipeline/*`, `library/README.md`, the former `shipped-delivery/SKILL.md`, `CLAUDE.md`, `remoto-studio/CLAUDE.md`.

## Where things live

- **This repo (`shipped`, public):** the Shipped site (Astro 7 + Tailwind v4, GitHub Pages), the `/start/` brief, pipeline scripts, the reusable `library/`, the production system (`.claude/`).
- **`../remoto-studio` (private):** everything carrying a real client's brand. One folder per project in `clients/<project>/`; the private preview in `deploy/shipped-concepts/`.
- Client material (briefs, photos, prototypes, PDFs) never enters this repo.

## Project folder

```
clients/<project>/
  brief.json          what /start/ sent (docs/build-flow.md)

  captures/           ideal, competitors, current site (pipeline/capture-brief.mjs)
  refs/               design systems of picked references (pipeline/ref-systems.mjs)

  site/               the build: v1 (all pages) + v2/ + v3/ home pages
  review/             visual.md, technical.md, release.md, review.md (script output)
  delivery.md         final delivery report
```

## Build stack for client sites

- Static HTML/CSS/JS generated by a `build-site.mjs` in the project folder (see `remoto-studio/clients/*/build-site.mjs`); page JS in modules or IIFEs; no framework unless the tech plan justifies one.
- Start from `library/`: the mobile menu and variant switcher always (the switcher is preview chrome: exempt from the client's palette and shapes, kept clear of sticky CTAs on phones), patterns and inspo components where the brief calls for them.
- New dependencies need a reason in `direction/tech.md`.
- **Open decision:** `strategy.md` §R names Framer as the production tool for delivered sites; the pipeline builds static prototypes. Until the owner decides, the build is a static site that can be handed over as is or rebuilt in the delivery tool.

## Checks

| Check | Command | Passes when |
|---|---|---|
| Rendered review | `node pipeline/review-site.mjs <project>/site` | All clear at 1440, 768 and a 390px touch phone: no overflow (also after scrolling to the bottom), h1 ≤ 3 lines, no broken or stretched images, no Shipped fonts, tap targets ≥ 44px, phone menu present, reduced motion handled, no console errors |
| Links | `node pipeline/check-links.mjs <project>/site` | no missing internal file or anchor (external links are listed for a manual check) |
| Client PDF | `node pipeline/make-client-pdf.mjs <project>` then `swift pipeline/render-pdf.swift` | no near-empty page before the roadmap, nothing internal on any page |
| Shipped site | `npm run build` | build completes |

The check is the truth: a red line beats any "looks fine". Report a check as passed only after running it.

## SEO basics

Every page: a title of about 50–60 characters and a meta description of about 140–160, `lang` set to the client's locale (e.g. `es-AR`), one h1, Open Graph title, description and image, a favicon, and structured data for the category when it fits (e.g. `Restaurant`, `LocalBusiness`, `Product`) carrying only facts the client supplied (never ratings or reviews we did not receive).

## Deployment and safety

- Client previews: private Vercel project `shipped-concepts`, built with `node tools/preview/build.mjs` in remoto-studio, `vercel deploy --yes` from `deploy/shipped-concepts`, public alias removed; verify the deployment URL answers 302 and the bare project domain 404.
- Never: deploy a client site to production, connect a client domain, merge to main of a client repo, touch live payments, billing, authentication, production databases or customer data, or spend on paid third-party services, without explicit owner approval in chat.
- Never write secrets to files; credentials live in environment variables or local ignored files.
- The Shipped site itself is committed and pushed after each change (standing owner instruction).
